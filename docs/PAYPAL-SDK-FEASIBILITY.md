# PayPal SDK feasibility — 17 October 2026

This record separates initial API/source research, local synthetic runtime tests and the later genuine hosted Sandbox rehearsal. The SDK agent performed source work and local tests without credential access or provider calls. Actual application setup, buyer actions and credentialed PayPal requests were performed by the parent agent; their saved sanitized receipts are identified below.

## Decision

Use the official Server SDK for the Agreements checkout adapter, keep the existing deterministic reconciliation rules, and use the official browser SDK for buyer approval. A shared milestone room, human consent and a hash-linked receipt are application features; they do not establish escrow, a decentralized network, identity verification, dispute resolution or final settlement. Each accepted milestone creates a separate ordinary merchant checkout order. No P2P or escrow API is assumed.

## Current SDKs

The npm registry and official source both report `@paypal/paypal-server-sdk` **2.5.0**, MIT, Node `>=14.17.0`. It ships ESM/CJS. Its current transport uses APIMatic's Axios adapter. Pin the version and preserve its notice. [Official manifest](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/package.json), [license](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/LICENSE).

`Client` supports explicit `Environment.Sandbox`, client-credentials OAuth, timeout, logging and HTTP options. Instantiate in code rather than importing arbitrary environment configuration. Default timeout is unlimited; set a bounded timeout. Default logger is null and retry count is zero; explicitly retain those safe choices. Never copy the README's body/header logging example into a credentialed demo. [Client](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/client.ts), [defaults](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/defaultConfiguration.ts).

Required controller calls are `OrdersController.createOrder({body,paypalRequestId,prefer})`, `getOrder({id})`, `captureOrder({id,paypalRequestId,prefer})`, and `PaymentsController.getCapturedPayment({captureId})`; results use `response.result`. Order creation is not payment. Buyer approval precedes capture. Keep idempotency keys stable across retries of the same operation and independently read captures after capture. [Orders controller](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/controllers/ordersController.ts), [Payments controller](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/controllers/paymentsController.ts).

SDK values use camelCase (`purchaseUnits`, `invoiceId`, `currencyCode`, `supplementaryData.relatedIds.orderId`), unlike current REST snake_case. Map only the required fields into `Observation`; discard payer/payee/address objects. [Order model](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/models/order.ts), [capture model](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/models/capturedPayment.ts).

## Worker compatibility

Project config has `nodejs_compat` and compatibility date `2026-10-17`. Some Node APIs remain partial or stubbed, so configuration alone is insufficient evidence. The actual SDK bundle now runs in real local Worker/SQLite tests with synthetic responses, and the parent subsequently completed the credentialed Sandbox path described below. [Cloudflare Node compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/).

There is no stable `fetch` injection option on the SDK Client. `unstable_httpClientOptions` is passed to the Axios client as `clientConfigOverrides`; the Axios adapter merges it into `axios.create`. The pinned custom Axios adapter enforces Sandbox URL/path allowlists, rejects redirects, uses Worker fetch, caps response bytes and implements cancellation. Merely adding `adapter:'fetch'` would not establish those bounds. Production code does not replace global fetch. [Configuration](https://github.com/paypal/PayPal-TypeScript-Server-SDK/blob/main/src/configuration.ts), [APIMatic HTTP adapter](https://github.com/apimatic/apimatic-js-runtime/blob/master/packages/axios-client-adapter/src/httpClient.ts).

### Confirmed pre-network failure and fix

The first credentialed hosted attempt returned an uncertain result before an Orders request was observed. Bounded receipt diagnostics identified `oauth` / `transport-error`, followed by `create-order` / `sdk-error`, without an HTTP response. A direct Node OAuth success did not establish Worker transport compatibility.

A no-network probe inside a real local Worker with the configured date/flags found that constructing a POST `Request` with `redirect: 'error'` threw `TypeError`; `manual` and `follow` constructed successfully. The current [Cloudflare Request documentation](https://developers.cloudflare.com/workers/runtime-apis/request/) lists all three modes, so this conclusion is tied to the tested runtime rather than inferred from that prose. Commit `83a7bbd` switches both `src/agreements/paypal-sdk.ts` and the original `src/core/paypal.ts` REST read adapter to `manual`. The SDK adapter rejects every 3xx before parsing; the REST adapter rejects every non-success response, including 3xx. Neither follows a `Location` header or forwards credentials to a redirect target.

The regression test constructs real Worker `Request` objects before returning synthetic OAuth/create/read responses; the complete SQLite workflow does the same. Node-only fake fetch tests had previously skipped this runtime validation. Separate redirect tests cover 301, 302, 303, 307 and 308 and assert one request only. After the fix was deployed, the parent retried the same persisted create attempt and obtained a genuine order.

Transport diagnostics now distinguish unsupported data, deadline, cancellation, fetch failure and rejected redirect using constant reason values. Only an allowlisted builtin error name, HTTP status, allowlisted provider name, bounded issue codes and hexadecimal PayPal debug ID can survive sanitization. The store revalidates and retains at most four diagnostics in an unconfirmed-operation receipt event. Messages, request bodies, authorization, arbitrary URLs, response descriptions and customer information are discarded. These diagnostics do not alter unknown-result handling or idempotency.

## Browser SDK

Current official v6 supports `loadCoreSdkScript({environment:'sandbox'})` from `@paypal/paypal-js/sdk-v6`, followed by `createInstance({clientId,components:['paypal-payments']})`. The browser client ID is public; the secret and OAuth access token remain server-side. A client ID does not select the SDK environment. Current types allow client ID or client token; some older prose still describes token-only authentication. Follow the current types and standard-checkout example. Do not add Fastlane or vaulting. [Official loader documentation](https://github.com/paypal/paypal-js/blob/main/packages/paypal-js/README.md), [current types](https://github.com/paypal/paypal-js/blob/main/packages/paypal-js/types/v6/index.d.ts).

`createPayPalOneTimePaymentSession` receives `onApprove/onCancel/onError`; `session.start({presentationMode:'auto'}, Promise<{orderId}>)` starts approval. Call start from a user click to preserve browser activation. In this app onApprove refreshes facts only. A separate human capture button triggers the server capture route; callback data never proves payment. [Payment session types](https://github.com/paypal/paypal-js/blob/main/packages/paypal-js/types/v6/components/paypal-payments.d.ts), [PayPal quick start](https://developer.paypal.com/checkout/integrate).

Initialization exposes loading, instance creation, eligibility and button preparation phases, with a 20-second overall deadline and late-result/unmount guards. A human-triggered stored-order approval route is available for loading/initialization failures; it is not offered to override explicit ineligibility or payment refusal. It creates or reuses the same server-bound order and then presents its validated approval link. It does not automatically navigate, approve, capture or mark payment complete. In the actual rehearsal the SDK became ready, but its popup was closed. Successful approval was demonstrated through the existing stored checkout link in a normal browser; a successful v6 `onApprove` callback remains unverified.

## Agent Toolkit and MCP alternatives

Registry/source report `@paypal/agent-toolkit` **1.11.0**. README requires Node18+. It imports several agent frameworks, Axios, OS helpers and Server SDK `^1.0.0`; installing it alongside SDK2.5 adds another SDK major. Published package metadata says ISC, while the repository's root license is Apache2.0: preserve both and resolve provenance before redistribution. [Package manifest](https://github.com/paypal/agent-toolkit/blob/main/typescript/package.json), [repository](https://github.com/paypal/agent-toolkit).

**Do not rely on toolkit environment defaults.** Current shared client and API code default `context.sandbox` to false. Explicit `configuration.context.sandbox:true` is mandatory. `actions:{orders:{get:true}}` limits enabled tools, whereas ALL_TOOLS_ENABLED permits payment mutations. `get_order` is available, but the listed toolkit has no separate fresh-capture-details tool. It cannot replace independent capture verification. Tool errors may contain provider descriptions; sanitize them before public output. [Client implementation](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/client.ts), [tool dispatch](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/api.ts), [tool filter](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/configuration.ts).

Official local MCP requires Node18 and supports explicit SANDBOX. Remote sandbox MCP is `https://mcp.sandbox.paypal.com/http` or `/sse`, with authentication/consent. Invoicing tools exist but would add merchant permissions, recipient records and outward messages; they are unnecessary for this milestone checkout. Do not use all-tools configuration or let model text directly create/capture/refund/send. [PayPal MCP guide](https://developer.paypal.com/ai-tools/mcp-server).

## Concrete implementation and release boundary

`src/agreements/paypal-sdk.ts`: sandbox-only SDK factory/transport, create/get/capture functions and fresh capture-to-Observation mapping. `src/agreements/store.ts`: persisted versioned terms, per-role capability hashes, dual consent, delivery acceptance, operation reservation/idempotency, bounded retention and receipt events. `src/agreements/router.ts`: strict schemas, role authorization, same-origin mutations, rate limits and generic errors. Existing `src/core/reconcile.ts` remains authoritative.

Terms freeze as soon as any checkout attempt is reserved, including uncertain failures. Amounts/invoice identity come from accepted server terms. Never derive them from browser callback data or AI output. Reserve state before provider awaits; retain stable request IDs across uncertain retries. A hash chain detects changes relative to a retained earlier anchor; without an independent anchor, an attacker can rewrite and recompute the entire packet. Capability possession is authority within this demo, not verified personal identity or a digital signature.

Public demo uses fictitious sandbox accounts, limited room creation/amounts/retention, no customer uploads, no secret in URL/query/logs, and no model financial actions. Prefer a dedicated sandbox app and encrypted Worker secrets. A verified SDK import, unit tests and fixture UI do not prove credentialed end-to-end PayPal success.

Hackathon requires meaningful PayPal sandbox plus AI, working judge access, public licensed source, English description and public YouTube demo under three minutes. Judging equally weights implementation, design, specific impact, innovation and presentation; adding frameworks alone earns no promised result. The final film must depict the actual functioning product. [Official rules](https://paypalaihackathon.devpost.com/rules).

## Implemented verification after the research pass

The Agreements adapter uses Server SDK 2.5.0 with an explicit custom Axios adapter, a hard Sandbox origin/path allowlist, redirect rejection, bounded 128 KiB JSON responses, a 15-second operation deadline and zero automatic retries. At commit `83a7bbd`, the SDK agent ran TypeScript, **93 npm tests**, and the frontend build successfully. A real Cloudflare Worker/SQLite Miniflare test bundles the actual SDK and exercises OAuth/create/get/capture/fresh-capture against an in-isolate synthetic provider. It verifies dual consent under concurrency, role restrictions, post-checkout terms freeze, one capture POST under synthetic concurrent requests, quota and expiry. These checks are distinct from the subsequent credentialed rehearsal.

The store reserves a persistent idempotency ID before each write operation, refuses a concurrent operation during its 30-second lease, and blocks uncertain write retries after five hours rather than assuming PayPal retains keys indefinitely. Refreshes keep the original write's first-attempt timestamp. Receipt verification binds exported room metadata to the hashed creation/latest-terms events and checks independent retained anchors at their prefix sequence.

Serialized capacity is separate from the 140-event count. A receipt export is capped at 384 KiB UTF-8; the verification HTTP envelope accepts 512 KiB, leaving room for `{packet,retainedAnchor}`. The complete private stored room is capped at 640 KiB. Before starting provider I/O, each pending operation reserves 64 KiB of receipt capacity and 112 KiB of stored-room capacity. All other mutations preserve those reservations. A current analysis is limited to 48 KiB; its duplicate appearance in the latest room view and receipt event fits the reserved room capacity. If a provider observation exceeds the supported size, a small generic failure event uses the reservation. Existing events are never pruned or rehashed to make space. A real Worker test fills a room through legitimate bounded delivery actions, verifies checkout is refused before any provider write at the byte boundary, and verifies the unchanged exported history against an earlier anchor.

Fallback approval links require the exact `https://www.sandbox.paypal.com` origin, the `/checkoutnow` path, no fragment or userinfo, a matching order token, and at most 2048 characters. The [official Orders integration sample](https://developer.paypal.com/whats-an-order/) returns this path. Unknown paths are omitted rather than linked; normal browser SDK approval can still use the validated order ID.
